# OJAS Context Assembly Governance

**Status:** Core governance draft  
**Scope:** Runtime context assembly, retrieval filtering, authority ranking, inclusion/exclusion, and context package governance.

---

## 1. Core principle

> **Memory retrieval does not equal context permission. Ojas must approve what enters the agent context.**

This is one of the most important runtime governance moments in Ojas.

---

## 2. Why context assembly matters

An agent acts based on what it is told.

If unauthorized, stale, poisoned, cross-tenant, or unapproved material enters context, later checks may be too late.

Context assembly enforces:

- tenant scope
- user scope
- domain scope
- memory authority labels
- source trust
- revocation status
- expiry status
- variant compatibility
- privacy and PII policy
- evidence sufficiency
- purpose limitation
- conflict handling
- prompt-injection screening
- budget/token constraints

---

## 3. Retrieval vs context

| Step | Meaning |
|---|---|
| Retrieval | candidates found |
| Filtering | disallowed candidates removed |
| Ranking | allowed candidates prioritized |
| Redaction | sensitive material removed or masked |
| Assembly | final model-visible context created |
| Recording | included/excluded items ledgered |

Rule:

> A retriever returns candidates. Ojas decides context.

## 6. Context candidate record

Every candidate carries provenance describing both the **content origin** (memory, tool, etc.) and the **producing-module trust state**. The producing-module trust state lets context assembly filter out material that came from a module which is not trusted, not variant-eligible, or not properly isolated for the current variant — even if the content itself looks otherwise admissible.

Example:

```json
{
  "candidateId": "ctx_cand_123",
  "sourceType": "SEMANTIC_MEMORY",
  "memoryId": "mem_456",
  "tenantId": "tenant-a",
  "authorityLabel": "MEDIUM_REVIEWER_APPROVED",
  "sourceTrust": "ENTERPRISE_POLICY_DOC",
  "effectiveFrom": "2026-01-01",
  "expiresAt": "2026-12-31",
  "revocationStatus": "ACTIVE",
  "variantOrigin": "standard",
  "retrievalScore": 0.82,
  "containsPII": false,
  "evidenceRefs": ["ev_789"],

  "producingModuleId": "ojas-memory-zep",
  "moduleTrustState": "trusted",
  "moduleVariantEligibility": "standard",
  "moduleCertificationStatus": "certified",
  "moduleIsolationMode": "in_process"
}
```

### 6.1 Module-trust fields

| Field | Meaning | Allowed values |
|---|---|---|
| `producingModuleId` | The module that produced or stored this candidate | a module identifier |
| `moduleTrustState` | Registry trust state of the producing module at the time the candidate was produced | `untrusted` / `trusted` / `revoked` |
| `moduleVariantEligibility` | The strictest variant for which the producing module is eligible | `open` / `standard` / `regulated` |
| `moduleCertificationStatus` | Current certification state of the producing module | `none` / `candidate` / `certified` / `expired` / `revoked` |
| `moduleIsolationMode` | How the producing module was running when it produced this candidate | `in_process` / `process_isolated` / `unknown` |

These values are **observed at production time** (when the candidate was created or last updated) and travel with the candidate. They are not re-derived at retrieval time, because a module's trust state may have changed since.

### 6.2 Module-trust filtering rules

The general rule:

> **Context generated by a backend or module that is not trusted, not variant-eligible, or not properly isolated for the current variant cannot enter context as authority.**

Specific filters:

| Producing-module condition | Effect on candidate |
|---|---|
| `moduleTrustState = untrusted` | Candidate excluded with `EXCLUDE_MODULE_TRUST` |
| `moduleTrustState = revoked` | Candidate excluded with `EXCLUDE_MODULE_REVOKED` |
| `moduleCertificationStatus in {expired, revoked}` and current variant requires certification | Candidate excluded with `EXCLUDE_MODULE_CERTIFICATION` |
| `moduleVariantEligibility` strictly weaker than current variant | Candidate excluded with `EXCLUDE_MODULE_VARIANT_ELIGIBILITY` |

For Regulated specifically:

> **Context generated by an in-process backend cannot be used as Regulated authority if that backend was required to be process-isolated.**

Operationally:

| Current variant | Producing-module isolation | Effect |
|---|---|---|
| Regulated | `moduleIsolationMode = in_process` | Candidate excluded with `EXCLUDE_MODULE_ISOLATION` |
| Regulated | `moduleIsolationMode = unknown` | Candidate excluded with `EXCLUDE_MODULE_ISOLATION` |
| Regulated | `moduleIsolationMode = process_isolated` | Candidate evaluated normally on other dimensions |
| Standard / Open | any | No isolation-based exclusion |

These exclusions are filters on **authority**, not visibility. A candidate excluded by module-trust filters MAY still be admissible as `INCLUDE_AS_UNTRUSTED_EVIDENCE` in Open or with explicit policy permission in Standard. In Regulated, module-trust filter failures exclude the candidate entirely.

### 6.3 Cross-references

The producing-module trust ladder, certification states, isolation modes, and revocation semantics are defined in the framework mechanics pack — specifically `OJAS_MODULE_SECURITY.md` and `OJAS_FRAMEWORK_DESIGN.md`. Context assembly **consumes** that state but does not define it.

## 8. Authority ranking

Ojas ranks context by authority and relevance, not relevance alone.

Suggested priority:

1. Identity Memory / manifest constraints
2. active policy/guardrail context
3. reviewer-approved Semantic Memory
4. authoritative enterprise tool outputs
5. admitted Episodic Memory
6. Session Memory
7. user input
8. external public/untrusted material
9. self-promoted Open memory
10. simulation/test memory

Rule:

> Lower-authority context cannot override higher-authority context.

---

## 9. Conflict handling

| Conflict | Ojas action |
|---|---|
| policy vs memory | policy wins |
| semantic memory vs user claim | semantic memory wins unless user provides authoritative evidence |
| reviewer-approved vs self-promoted | reviewer-approved wins |
| current tool result vs stale memory | tool result may be evidence; stale memory may be downgraded |
| Regulated context vs Open-origin memory | Open-origin memory cannot be authority |
| revoked memory retrieved | exclude and record |
| expired memory retrieved | exclude or mark stale |
| simulation vs production authority | simulation cannot become production authority |
| candidate from untrusted module vs trusted equivalent | trusted-module candidate wins; untrusted-module candidate excluded as authority |
| candidate from in-process backend vs Regulated requirement | excluded from Regulated authority |
| candidate from module with expired/revoked certification | excluded if current variant requires certification |

---

## 10. Variant behavior

| Context feature | Open | Standard | Regulated |
|---|---|---|---|
| unreviewed memory | allowed with label | restricted | excluded from authority |
| self-promoted memory | allowed with label | context only with warning | excluded as authority |
| external public content | allowed | source trust required | restricted/evidence only |
| tool result | allowed | classified | classified + evidence-linked |
| semantic memory | allowed if in scope | reviewer-approved preferred | reviewer-approved required |
| vector results | allowed | authority-filtered | authority-filtered + audited |
| graph results | allowed | source authority inherited | source authority inherited + evidence |
| simulation memory | allowed | not production authority | excluded from production authority |
| candidate from untrusted module | allowed with label | excluded from authority | excluded entirely |
| candidate from in-process backend | allowed | allowed | excluded from authority |
| candidate from process-isolated backend | allowed | allowed | required for authority |
| candidate with expired/revoked module certification | allowed with label | excluded from authority | excluded entirely |

## 11. Context package

The runtime receives a context package, not raw retrieval output.

Example:

```json
{
  "contextPackageId": "ctx_pkg_123",
  "tenantId": "tenant-a",
  "variant": "standard",
  "agentId": "invoice-review-agent",
  "includedItems": [
    {
      "candidateId": "ctx_cand_123",
      "role": "POLICY_CONTEXT",
      "authorityLabel": "MEDIUM_REVIEWER_APPROVED",
      "contentRef": "redacted-or-inline-content",
      "evidenceRefs": ["ev_789"]
    }
  ],
  "excludedSummary": {
    "revoked": 1,
    "scopeMismatch": 2,
    "variantMismatch": 1
  }
}
```

## 12. Tool results and context

Tool outputs must not be injected directly.

Flow:

```text
Tool output
  ↓
Tool output classification
  ↓
Source trust label
  ↓
Optional memory admission
  ↓
Context assembly decision
  ↓
Model-visible context
```

Rule:

> Tool result is not context until Ojas includes it.

---

## 13. Projections and context

Vector and graph systems return candidates.

```text
Vector search → candidates
Graph traversal → candidates
Search cache → candidates
Ojas context assembly → permission
```

Rules:

> Retrieval score is not authority.  
> Graph inference is not authority.  
> Cache hit is not authority.

## 15. Context invariants

1. Retrieval is not permission.
2. Relevance is not authority.
3. Context inclusion is an Ojas decision.
4. Revoked memory never enters context.
5. Expired memory cannot enter context as authority.
6. Open-origin memory cannot become Regulated authority.
7. Lower-authority context cannot override higher-authority context.
8. Tool outputs must be classified before context inclusion.
9. Graph/vector/cache results inherit source authority only.
10. Every included and excluded context item must be recorded.
11. Context generated by an untrusted, revoked, variant-ineligible, or improperly isolated module cannot enter context as authority.
12. Producing-module trust state is observed at production time and travels with the candidate.
